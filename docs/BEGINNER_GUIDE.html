Accelerator Beginner Guide

What the project files are, why each one exists, and exactly what to type. Written for someone who can simulate Verilog in Xcelium but has never seen the Python, C or script parts.

Everything in this guide was checked on the real files, with one limit: I do not have Xcelium, ModelSim, Genus or Innovus here. The simulation was tested on another 4-state simulator (Icarus) with identical results; the commands for your tools are written carefully but were not run on them. Section 11 says what to do if one fails.

1. The story in plain words

The chip recognises handwritten digits. You give it a tiny 8×8 grey picture (64 numbers), it does a fixed amount of arithmetic, and it answers with ten scores, one per digit 0–9. The biggest score is its guess.

Analogy. Think of the chip as a vending machine that has ten judges inside. Each judge looks at the 64 pixels and gives a score for "how much does this look like my digit". The judges' preferences are a big table of numbers called weights. Somebody has to teach the judges (training), write their preferences down in whole numbers the machine can handle (quantization), and press the machine's keypad once for every number (loading). The machine itself never does any of that: it only does the arithmetic.

That "somebody" is the reason there is a Python folder, a C folder and a build folder. Figure 1 shows the whole chain. Blue boxes are Python on your PC. Green boxes are Verilog running inside the simulator.

The file prog.hex is the link between the two halves. It is plain text, 9 677 lines: 9 676 keypad presses, one per line, plus a final END marker. Here is the beginning of it, decoded:

Line in prog.hexSplit intoMeaning
03000004d44a010003 · 00 · 0004 · d44a0100Operation 03 = "read and check". Read register number 4 (the chip's ID) and complain unless it equals d44a0100. It proves the testbench is talking to the right chip.
01001000fbfd040001 · 00 · 1000 · fbfd0400Operation 01 = "write". Put the value fbfd0400 at address 1000, which is the start of the weight memory. That value packs four weights (0, 4, −3, −5) into 32 bits.

The remaining lines load all 304 rows of weights, the biases, a description of each layer, then the pictures, then press START, wait, and read the answers back. The chip's own registers and memories are all reached the same way: an address and a number.

2. Basics from zero

2.1 What "the neural network" is here

It is two layers of multiplication and addition. Nothing else. For one picture:

StepWhat happensShape of the numbers
Inputthe 8×8 picture, flattened into one row of 64 numbersx : [1 × 64]
Layer 116 "neurons". Each one multiplies all 64 pixels by its own 64 weights and adds them up, then adds a bias number. Negative results become 0 (this is called ReLU).x [1×64] · W1 [64×16] + b1 [16] → h [1×16]
Layer 210 neurons, one per digit, each looking at the 16 numbers from layer 1h [1×16] · W2 [16×10] + b2 [10] → scores [1×10]
Answerthe position of the biggest scoreargmax → one digit

A real example from this project (picture number 0, which is a handwritten 7): neuron 5 of layer 1 multiplies 64 pixel values by 64 weights and adds them up to 29 657, adds its bias 4 550 to get 34 207, and rescales that to 45. Layer 2 then gives the ten scores [−8, −14, −24, −10, −3, −27, −34, 34, −4, 20]. The biggest is 34 at position 7. The chip says "7". You can see every such number yourself with python sw\trace_one.py 0 5 (section 8).

The weights are the only thing that was "learned". Training (with a library called PyTorch) tried thousands of values until the guesses on known pictures were right. That already happened; the result is in build/model.onnx.

2.2 What "MAC" means, and why it is the whole game

A MAC is one multiply followed by one add: total = total + weight × pixel. Layer 1 needs 64 × 16 = 1 024 of them, layer 2 needs 16 × 10 = 160, so 1 184 MACs per picture. A neural-network chip is a machine for doing MACs cheaply. Doing them is easy; the expensive part is fetching the weights and pixels from memory, so the design is built to fetch each number as few times as possible.

2.3 What "systolic array" means

Analogy. A bucket brigade. Instead of every worker walking to the warehouse, each worker hands the item to the next person in the line. Here the "workers" are 16 small multiply-add circuits (PEs, processing elements) in a 4×4 grid. Each PE keeps one weight for a while, pixels flow across the grid from the left, and running totals flow down. Nobody talks to the big memory except at the edges.

A 4×4 array only sees 4 pixels and 4 neurons at a time, but the network has 64 pixels and 16 neurons. So the controller (rtl/dnn_ctrl.v) cuts the work into tiles: layer 1 becomes 16 × 4 = 64 tile-runs ("passes"), layer 2 another 12. In each pass it loads 4×4 = 16 weights (4 clocks), streams the 8 pictures of a batch through (8 clocks), and waits for the pipeline to empty (about 11 clocks). Partial totals from different tiles are added in a small memory. Everything in this paragraph is done by RTL you already have; you only need to know why the waveform looks the way it does.

2.4 Why 8-bit integers ("INT8")

Trained weights are decimals such as 0.0168. Decimal (floating-point) maths costs roughly ten times or more energy than 8-bit integer maths, so before the chip sees them each number is converted: pick a scale (0.01685 for layer 1), divide, round to a whole number between −127 and 127. This step is quantization and lives in sw/quantize.py. The price is a tiny accuracy loss; here there is none: the decimal network scores 96.94 % on 360 unseen pictures, and so does the integer network, and so does the chip.

The chip's integer sums are large (like 34 207), so the last stage shrinks them back to 8 bits with a "multiply by 44203, then shift right by 25 bits" step. That equals multiplying by 0.001317 without needing a decimal multiplier.

2.5 Why the chip cannot run by itself

The chip has memories that start empty and registers that start at zero. To use it, something must (1) write 304 rows of weights into the weight memory, (2) write the biases and a "work order" for each layer, (3) write the picture into the input memory, (4) write 1 to the START register, (5) wait until DONE, (6) read the answers back. In a real product a small CPU does this by running driver software. In your simulation the testbench does it by replaying prog.hex. Same steps, different actor. Section 3 shows this side by side (Figure 3).

3.1 rtl/ and tb/: what you already understand

RTL is the chip: registers and logic written in Verilog. The files you would use if you were building the chip are all in rtl/. The top-level module is dnn_accel_top (or dnn_accel_axil_top, the same chip with an AXI bus plug on the front). Files starting with accel_ctrl or systolic_accel_top belong to the first, simpler version and are not part of the DNN design.

A testbench is Verilog that is not the chip; it exists only to poke the chip in simulation. tb/tb_dnn_player.v is a "player": it reads a program file (prog.hex), and for each line writes or reads one chip register, exactly as a CPU would. It counts mismatches and prints PLAYER PASSED or PLAYER FAILED.

3.4 driver/: what a "driver" is, and why you never run it

A driver is the program on the processor that knows how to talk to a piece of hardware. Your keyboard, GPU and Wi-Fi card all have one. For this chip, the driver is about 250 lines of C: dnn_load_network() writes weights and layer descriptions, dnn_write_input() writes a picture, dnn_run() presses START and waits, dnn_read_output() reads the ten scores.

It exists for two reasons. First, a chip without software is unusable, so a complete project shows how software would use it. Second, it is an independent check: I made the C driver produce its own list of register writes and compared it with the Python compiler's list. They match on all 568 accesses of the first batch, which means the register map documented in docs/05 is really what the chip does, and not just what one program believes. That is the whole reason for it. The C code is not needed for your simulation, and you cannot run it on your PC in any useful way because there is no chip attached.

3.5 scripts/: what a script is

A script is a text file containing commands you would otherwise type one by one. A .sh file is a script for a Linux shell; a .bat file is the Windows equivalent. Running a script just means "type all the commands in that file for me". Nothing magic.

The scripts in scripts/ are mine. They build the chip with Verilator (a free simulator), run it, and compare results. You do not have Verilator, so you use the equivalents in cadence/, which call Xcelium or ModelSim instead:

6. Job 1: run the simulation

Goal: make the simulator run all 360 test pictures through your chip and print PASSED. What happens inside: the testbench reads build/prog.hex line by line, pushes each line into the chip as a register write or read, and compares every answer with the expected one that is already stored inside the file.

You do this

Make sure your terminal is standing in the systolic_dnn_accel folder (section 5, steps 2 and 3). Then follow Setup A or Setup B, not both.

Setup A: ModelSim on Windows

  1. Type the launch command.

    Type in: Windows cmd, inside systolic_dnn_accel
    cadence\run_modelsim.bat

    Or, in File Explorer, open the cadence folder and double-click run_modelsim.bat. It does the same and keeps its window open at the end. If Windows shows a blue "protected your PC" box, click More info, then Run anyway.

  2. Wait. ModelSim first compiles the 16 Verilog files (the testbench plus the 15 design files; a few seconds), then simulates about 0.9 milliseconds of chip time. This takes from under a minute to a few minutes depending on the ModelSim edition.

  3. Find the result near the bottom of the window.

If the .bat file does not work for any reason, this single command does the same thing (it needs vsim to be found too; if cmd says "vsim is not recognized", read the first row of the table in section 11):

Type in: Windows cmd, inside systolic_dnn_accel
vsim -c -do cadence/run_modelsim.do

Setup B: Xcelium on Linux

  1. Type the launch command.

    Type in: Linux terminal, inside systolic_dnn_accel
    bash cadence/run_xcelium.sh

    (Use bash even if your terminal uses another shell; the file is written for bash.) The script checks that xrun exists, then runs it with the right file list and settings. It creates a few temporary files (xcelium.d, xrun.log) that you can delete later.

  2. Wait a few minutes at most.

  3. The last line of the output tells you the result.

What a good result looks like

The simulator prints many of its own lines. Look for these two, which come from the testbench, and for the last line of the Xcelium script:

PLAYER: 9677 ops, 1313 reads, 0 mismatches, 0 timeouts, 79785 cycles polling
*** PLAYER PASSED ***
(Xcelium script only, last line:)
>>> RESULT: PASSED  (readback written to build/rtl_readback.txt)

What each number means:

ItemMeaning
9677 opsThe testbench executed all 9 677 lines of prog.hex (the last one is the END marker).
1313 readsIt read 1 313 values back from the chip. Of these, 1 088 were checked against the expected answer stored in the file: 8 ID/configuration registers plus 1 080 answer words (45 batches × 8 pictures × 3 words per picture). The other 225 are speed counters that are only logged.
0 mismatchesEvery one of the 1 088 checks matched. This is the number that proves the chip is correct.
0 timeoutsThe chip never got stuck waiting for itself.
79785 cycles pollingHow long the testbench waited for the chip to finish, in clock cycles. It should be the same on your simulator; if it differs by a few cycles that is not a problem.
Harmless warnings

You will probably see a warning that $readmemh found fewer words than the memory it is filling (the memory has room for 262 144 lines and the file has 9 677). Some simulators also print a warning about missing timescales, or about unused parameters. If the two lines above appear, ignore the warnings.

If you see FAILED

Copy the first ten lines that contain FAIL or MISMATCH, plus the tool name and version, and send them to me. Section 11 lists the usual causes first.

Optional second run: through the AXI bus

The same test, but the testbench talks to the chip through an AXI4-Lite bus plug (the standard way a processor connects to a peripheral), with random delays. It should also pass.

7. Job 2: look at the waveform

A waveform shows every chosen signal as a line against time. You will use it to see the chip's state machine working through the network, and to take screenshots for your report. The waveform uses only the first batch (8 pictures; about 2 400 clock cycles in all, of which the chip itself is busy for 1 771), so it opens quickly.

Setup A: ModelSim

  1. Launch.

    Type in: Windows cmd, inside systolic_dnn_accel
    cadence\run_modelsim.bat gui

    The ModelSim window opens, compiles, simulates and fills the Wave window with the interesting signals already grouped under headings. If a box ever asks "Are you sure you want to finish?", click No: Yes closes ModelSim and your waveform with it.

  2. If the Wave window looks empty or cramped, click on it once, then press f (zoom full). To zoom into a region, hold Ctrl and use the mouse wheel, or drag with the middle mouse button.

  3. Click anywhere in the waveform to place a cursor. The value of every signal at that time appears in the left column.

Setup B: Xcelium (SimVision)

  1. Launch.

    Type in: Linux terminal, inside systolic_dnn_accel
    bash cadence/run_xcelium.sh --gui

    SimVision opens with a Design Browser window (a hierarchy tree on the left, signal list on the right) and a Console window with a command prompt. The simulation is loaded but paused at time 0.

  2. In the Design Browser, expand the tree on the left by clicking the small triangle or plus sign next to: tb_dnn_player → g_reg → dut → u_core → u_ctrl. The right side now lists the controller's signals.

  3. Click state. Hold Ctrl and click layer_cnt, kt_cnt, nt_cnt, m_cnt, busy, done, err. Then click the toolbar button that sends selected signals to a waveform (its tooltip says "Send to Waveform Window"; it is also in the right-click menu). A Waveform window appears.

  4. Go back to the tree and repeat step 3 for these places:

    • tb_dnn_player: signals clk, reg_wr_en, reg_addr, reg_wdata
    • tb_dnn_player → g_reg → dut → u_core: signals acc_wr_en, acc_rd_en

9. Job 4: synthesis in Genus

Jobs 1–3 proved the design works. Job 4 answers the next question a chip person asks: how big is it, how fast can it run, how much power does it use? Only a synthesis tool can tell you, and Genus is yours.

9.1 What synthesis is

Analogy. Your Verilog is an architect's drawing: "here is a room that adds two numbers". A builder cannot order a drawing; a builder orders parts from a catalogue. Synthesis is the step that turns the drawing into a parts list: "12 000 NAND gates of catalogue type NAND2X1, 32 000 flip-flops of type DFFQX1, joined by these wires". The catalogue belongs to a chip factory and is called a standard-cell library; its file is a .lib. For every cell it lists delay, area and power. Genus adds these up to give you the three numbers for the report.

How to read slack

Slack ≥ 0: the design meets the 10 ns clock you asked for. Slack < 0: too slow. Either way the fastest clock the design can take is roughly period − slack, with both in the same unit (convert ps to ns first: 1 300 ps = 1.3 ns).

Example A (numbers invented): period 10 ns, slack +1.3 ns → about 8.7 ns → 1000 / 8.7 ≈ 115 MHz.
Example B: period 10 ns, slack −2.0 ns → about 12 ns → 1000 / 12 ≈ 83 MHz.

To find the real limit, change the clock period and rerun:

  1. Open cadence/constraints.sdc and edit the line set clk_period 10.0. Put the value you computed (for example 12.5 after example B, so you have a little margin) and save.

  2. Run the same genus -f ... command again. Slack should now be ≥ 0.

  3. Report the smallest period that still gave slack ≥ 0 as your maximum clock, together with its area and power. Area and power change slightly with the period, so always quote all three numbers from the same run.

9.5 Two things to say honestly in your report

  • The memories became flip-flops. The design's memories are written as plain Verilog arrays (rtl/sram_sdp.v), so Genus builds each stored bit from a flip-flop: 30 976 bits in the five memories plus 1 024 bits in the layer-description store. A real chip would use compiled SRAM macros, which are much smaller. Say so, and treat the area as an upper bound. (docs/06, section 3 explains how to swap them.)
  • The power is a statistical guess. Without an activity file Genus assumes how often signals switch. A better number uses the simulation's own activity (docs/06 mentions read_vcd and report_power). For a first report, quote the estimate and label it an estimate.

9.6 Turning the numbers into speed and energy

The simulation gave you cycles (1 771 per batch of 8 pictures, 221.4 per picture). Synthesis gave you a clock frequency f and a power P. Multiply:

Analogy. Genus wrote the parts list. The result is a layout, the file a foundry would manufacture from.

10.3 A report outline that fits this project

  1. Motivation: why neural-network inference needs dedicated hardware (many multiply-adds, mostly the same weights reused).
  2. The network and INT8 quantization: 64→16→10, why whole numbers are enough (Figure 1 and section 2 of this guide; docs/01).

  5. Results: tables 10.1 and 10.2, the waveform screenshots from Job 2, the cycle breakdown.
  6. Discussion: 33.4 % utilization and why (each pass spends 4 cycles loading weights, 8 computing and about 11 draining the pipeline, so the array computes for roughly a third of the time); the 2.25 bytes per MAC finding; flip-flop memories; what a bigger array does (docs/04 roadmap).
  7. Limits and future work: SRAM macros, place and route, larger networks.
If your guide asks: "why Python and C?"

The chip only multiplies and adds whole numbers, so something outside it must train the network, convert it to whole numbers and plan which memory address each number goes to; that is the Python part. In a real product a processor would press the chip's registers by running a program, and the C driver is that program; in this project the testbench plays the processor. The C driver is included, and tested to produce exactly the same register writes as the Python compiler, to show that the chip is usable by real software and that its register map is documented correctly.
